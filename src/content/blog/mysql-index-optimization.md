## 慢查询的发现

线上服务突然出现接口超时告警，P99 延迟从 50ms 飙升到 3s。第一时间查看慢查询日志：

```sql
SELECT * FROM orders 
WHERE user_id = 12345 
AND status = 'pending' 
ORDER BY created_at DESC 
LIMIT 20;
```

## EXPLAIN 分析

执行 `EXPLAIN` 后发现：

```
+----+-------------+--------+------+---------------+------+---------+------+--------+-----------------------------+
| id | select_type | table  | type | possible_keys | key  | key_len | ref  | rows   | Extra                       |
+----+-------------+--------+------+---------------+------+---------+------+--------+-----------------------------+
|  1 | SIMPLE      | orders | ALL  | NULL          | NULL | NULL    | NULL | 500000 | Using where; Using filesort |
+----+-------------+--------+------+---------------+------+---------+------+--------+-----------------------------+
```

**问题**：全表扫描 + filesort，50万行数据中找 20 行。

## 索引设计

根据查询条件，我们设计了联合索引：

```sql
ALTER TABLE orders 
ADD INDEX idx_user_status_time (user_id, status, created_at DESC);
```

### 为什么是这个顺序？

1. `user_id`：等值查询，区分度高，放最前
2. `status`：等值查询，放中间
3. `created_at`：排序字段，利用索引有序性

## 优化效果

```
+----+-------------+--------+------+-----------------------+----------------------+---------+-------------+------+-----------------------+
| id | select_type | table  | type | possible_keys         | key                  | key_len | ref         | rows | Extra                 |
+----+-------------+--------+------+-----------------------+----------------------+---------+-------------+------+-----------------------+
|  1 | SIMPLE      | orders | ref  | idx_user_status_time  | idx_user_status_time | 12      | const,const |  150 | Using index condition |
+----+-------------+--------+------+-----------------------+----------------------+---------+-------------+------+-----------------------+
```

**优化结果**：

- 扫描行数：500,000 → 150
- 查询时间：3.2s → 8ms
- P99 延迟恢复正常

## 经验总结

1. **慢查询日志是第一时间排查工具**
2. **EXPLAIN 是理解查询计划的钥匙**
3. **联合索引的顺序很重要** — 等值字段在前，范围/排序字段在后
4. **覆盖索引** — 如果查询字段都在索引中，可以避免回表

> 索引不是越多越好。每个索引都会增加写入成本，要在读写之间找到平衡。
